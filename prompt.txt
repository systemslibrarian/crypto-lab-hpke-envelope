- Repo name:         crypto-lab-hpke-envelope
- Short name (H1):   HPKE Envelope
- Subtitle:          Hybrid Public Key Encryption · RFC 9180
- One-liner:         Real HPKE with every stage exposed and clickable — a KEM, a KDF, and an AEAD composed into one scheme, each stage linking out to the lab that teaches it alone.
- Concept to teach:  HPKE is not a primitive. It is three primitives plus a key schedule that binds them to a context. The security lives in the binding: change the info string, the AAD, or the mode, and the same three primitives produce a different key — which is the point, and also where composition breaks.
- Primitives/spec:   HPKE (RFC 9180): DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + AES-128-GCM / ChaCha20-Poly1305; modes Base/PSK/Auth/AuthPSK; KeySchedule §5.1; RFC 9180 Appendix A test vectors. Named-not-built: MLKEM768-X25519 hybrid KEM (draft-ietf-hpke-pq, now in Go's crypto/hpke).
- Accent (--accent): #1D4ED8
- Favicon emoji:     ✉️
- In scope:
    * Real HPKE, hand-rolled key schedule over @noble/curves + @noble/hashes + WebCrypto AEAD. RFC 9180 Appendix A KATs (state the count — A.1 Base/PSK/Auth/AuthPSK at minimum).
    * THE COMPOSITION SURFACE — this is why the lab exists. The pipeline is drawn as three linked stages:
        recipient pkR → [KEM: Encaps] → shared_secret → [KDF: KeySchedule] → key+base_nonce+exporter_secret → [AEAD: Seal] → ct
      Every stage is a real computation with real intermediates AND a link out: KEM → kyber-vault / curve-lens, KDF → kdf-chain, AEAD → aes-modes / ascon / aegis-gate. Clicking a stage expands its internals in-page; the link opens the full lab.
    * Mode switcher: Base / PSK / Auth / AuthPSK. Show what each adds to the key schedule input (psk_id_hash, the Auth KEM's extra DH), and what each proves. Show the key schedule inputs changing byte-for-byte as the mode changes.
    * Context-binding break-it: edit `info`, edit the AAD, change the mode on one side only. Sender seals, receiver opens, real AEAD rejects. The learner causes it.
    * Sequence/nonce panel: base_nonce XOR seq. Show the nonce evolving per Seal. Link to nonce-collision for what happens if it doesn't.
    * Honest non-goals panel drawn from RFC 9180 §9.7 itself: HPKE gives NO forward secrecy (Base mode), no downgrade or replay prevention, no plaintext length hiding, no protection against bad ephemeral randomness. These are the spec's own stated non-goals and they are the setup for ECH, OHTTP, and Entropy Collapse. Link each.
    * PQ panel (named, not built): MLKEM768-X25519 as an HPKE KEM — the composition is why HPKE absorbed post-quantum by swapping one stage. Link hybrid-wire.
- Non-goals:         Do NOT rebuild the KEM math (kyber-vault/curve-lens own it), the KDF comparison (kdf-chain), or the AEAD internals (aes-modes/aegis-gate) — expose and link. No ECH (separate lab). No OHTTP (separate lab). No key-compromise-impersonation attack build-out — RFC 9180 §9.1 states DHKEM's KCI limitation; name it.
